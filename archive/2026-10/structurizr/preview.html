다이어그램은 남지만 구조는 남지 않는다

아키텍처 다이어그램은 대개 회의 직후에 만들어진다. 발표 자료에 한 장 넣고, 위키에 붙이고, 그걸로 끝난다. 만든 사람은 구조를 알고 있으니 충분하다고 느낀다. 문제는 6개월 뒤Services가 분할될 때, 그림은 그대로인데 어떤 요소가 왜 추가됐는지, 어떤 관계가 사라졌는지 아무도 설명하지 못한다. 그림은 남았지만, 구조를 결정했던 판단은 남지 않는다.

Structurizr, 모델로 구조를 잡는다

Structurizr는 이 문제를 '그림'이 아니라 '모델'로 해결한다. 이 글에서는 설치 없이 확인하는 방법, DSL의 기본 구조, 저장소에 넣는 운영 방식, 그리고 어디까지 믿어야 하는지까지 정리했다.

이 글에서 확인할 것

· 단일 모델과 다중 뷰의 차이

· 설치 없이 5분 안에 확인하는 방법

· DSL 기본 구조와 내보내기

· 모델을 믿을 때 확인할 한계

Structurizr란 무엇인가

Structurizr는 C4 모델을 위한 models as code 도구다. C4 모델의 creator인 Simon Brown이 직접 만들었고, 지금도 C4 모델을 가장 정확하게 따르는 레퍼런스 구현을 유지하고 있다.

핵심은 도구가 아니다. 아키텍처를 Structurizr DSL이라는 텍스트로 적고, 그 파일에서 다이어그램을 파생시킨다. 파일을 Git에 넣고, 변경은 diff로 남긴다. 그림은 결과물이고, 모델이 원본이다. 원본이 텍스트라면 리뷰도 버전 관리도 가능하다.

한 모델, 여러 뷰

Structurizr에는 두 층이 있다. 모델은 요소(person, softwareSystem, container, component)와 그 관계를 포함한다. 뷰는 모델을 특정 관점에서 잘라 보여주는 표현이다.

같은 모델에서 시스템 컨텍스트, 컨테이너, 컴포넌트, 동적, 배포 뷰를 생성한다. 요소를 하나 추가하면 관련된 모든 뷰에 자동으로 반영된다. 그림마다 손으로 고치던 불일치가 구조적으로 사라지는 이유다.

그래서 하나의 원칙이 생긴다. 뷰를 고치는 대신 모델을 고친다. 이 규칙 하나가 문서와 실제 구조 사이의 간격을 줄인다.

설치 없이 확인하기

가장 빠른 방법은 플레이그라운드다. 브라우저에 DSL을 붙여 넣으면 바로 렌더링된다. 도구를 설치하지 않고 문법과 뷰의 관계를 익힐 수 있다.

로컬에서 실행하려면 Docker 이미지 하나면 충분하다. 데이터 디렉터리를 마운트하면 첫 실행 시 workspace.dsl이 자동으로 만들어진다.

docker pull structurizr/structurizr
docker run -it --rm -p 8080:8080 -v PATH:/usr/local/structurizr structurizr/structurizr local

http://localhost:8080을 열면 요약 페이지가 나온다. DSL을 저장하고 새로고침하면 그림이 바뀐다. 레이아웃은 편집기에서 조정하고, 변경은 몇 초 간격으로 자동 저장된다.

DSL 기본 구조

DSL은 세 블록으로 시작한다. workspace, model, views. 사람과 시스템을 정의하고, 관계를 화살표로 잇고, 뷰에서 담을 범위를 정한다.

workspace {
  model {
    u = person "User"
    ss = softwareSystem "Software System"
    u -> ss "Uses"
  }
  views {
    systemContext ss {
      include *
    }
  }
}

person과 softwareSystem은 요소, 화살표는 관계다. views 안에서 systemContext 뷰를 선언하고 include *로 전체를 담는다. 요소를 추가해도 뷰 선언은 그대로 두고, 그림만 갱신된다.

규모가 커지면 container, component, deployment, dynamic 뷰를 더한다. 요소 식별자(u, ss)를 명시하면 다른 파일에서도 같은 요소를 참조할 수 있어, 모델을 여러 파일로 나눌 수 있다.

뷰 내보내기

운영에서는 CLI로 내보낸다. 위키나 빌드 산출물에 넣을 정적 이미지가 필요할 때 사용한다.

structurizr-cli export -workspace workspace.dsl -format plantuml

형식은 plantuml, c4plantuml, mermaid, websequencediagrams, png, svg, static site 등을 지원한다. Mermaid로 내보내면 GitHub이나 사내 위키에서 별도 도구 없이 렌더링된다.

뷰 시스템 컨텍스트 이 시스템은 누구와 무엇에 연결되나
컨테이너 배포 단위는 무엇이고 어떻게 통신하나
컴포넌트 컨테이너 내부 책임은 어떻게 나뉘나
동적 한 시나리오에서 호출이 어떤 순서로 흐르나
배포 어떤 환경의 어떤 노드에 올라가나

실무 적용: 저장소에 넣는 방법

가장 단순한 운영은 docs/architecture/workspace.dsl 한 파일이다. 코드와 같은 저장소에 두면, 아키텍처 변경은 코드 변경과 같은 PR에서 리뷰된다.

절차는 세 줄이면 된다. 모델을 고친다 → 검사한다 → PR에 뷰 이미지를 첨부한다. 리뷰어는 그림이 아니라 diff를 본다. 요소가 언제 왜 늘어났는지가 텍스트로 남기 때문이다.

결정의 배경은 ADR으로 분리한다. DSL은 구조를, ADR은 이유를 담당한다. 둘을 링크해 두면 6개월 뒤에도 "왜 이렇게 됐는지"를 복원할 수 있다.

CI에는 검사와 내보내기를 넣는다. 모델이 깨지면 빌드가 실패하고, 문서는 항상 최신 상태로 배포된다.

한계와 주의

Structurizr는 코드를 읽어 구조를 추출하지 않는다. 모델은 사람이 직접 적는다. 그래서 코드가 바뀌어도 모델이 자동으로 따라오지 않는다.

C4의 컴포넌트 뷰는 코드 구조와 가깝지만,それも 자동 추출이 아니다. "모델이 코드와 다르다"는 문제는 도구가 아니라 운영 규칙으로 막아야 한다.

DSL은 학습이 필요하고, 레이아웃은 여전히 손으로 조정한다. 요소가 수백 개로 늘면 모델을 나누고 이름 규칙을 정하는 비용도 든다.

정리하면 Structurizr는 "그림 자동 생성기"가 아니라 구조를 합의하는 문서 형식에 가깝다. 그 점을 기대하고 도입하면 만족도가 높다.

검증 루틴

1단계. 모델의 요소가 실제 배포 단위와 일치하는지 확인한다. 컨테이너가 코드의 서비스와 1:1로 대응하지 않으면, 뷰를 읽는 사람은 곧바로 혼란을 겪는다.

2단계. 관계의 방향을 확인한다. A → B는 "A가 B를 호출한다"는 뜻이다. 데이터 흐름과 호출 방향이 뒤섞이면 다이어그램이 거짓말을 한다.

3단계. 변경 내용을 diff로 읽는다. 요소 추가·삭제가 PR에서 보이면 리뷰가 쉽다. 반대로 그림만 바뀌는 변경은 오히려 경계 신호다.

4단계. 검사를 자동화한다. 문법 오류와 참조 오류를 사람이 눈으로 찾지 않게 만든다.

정리

Structurizr의 가치는 예쁜 다이어그램이 아니다. 구조를 텍스트로 남겨 리뷰와 버전 관리의 대상으로 만드는 데 있다.

모델 하나에서 여러 뷰를 파생내면 불일치가 줄어들고, Git에 두면 변경 이유가 남는다. 다만 모델은 자동으로 최신이 되지 않으므로, 코드 변경과 같은 PR에서 갱신하는 규율이 필요하다.

새 프로젝트에 합류했을 때, 아키텍처 리뷰를 준비할 때, 문서가 코드와 어긋나기 시작했다고 느낄 때 한 번 도입을 검토해 볼 만하다.
