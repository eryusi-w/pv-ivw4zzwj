다이어그램은 남지만 구조는 남지 않는다

아키텍처 다이어그램은 대개 회의 직후에 만들어집니다. 발표 자료에 한 장 넣고, 위키에 붙이고, 그걸로 끝납니다. 만든 사람은 구조를 알고 있으니 충분하다고 느낍니다.

문제는 6개월 뒤에 드러납니다. 서비스가 둘로 쪼개졌는데 그림은 그대로입니다. 어떤 요소가 어떤 근거로 추가됐는지, 어떤 관계가 사라졌는지 아무도 설명하지 못합니다. 그림은 남았지만 구조를 만든 판단은 남지 않았습니다.

Structurizr는 이 문제를 "그림"이 아니라 모델로 옮깁니다. 이 글은 설치 없이 확인하는 방법, DSL의 기본 구조, 저장소에 넣는 운영 방식, 그리고 어디까지 믿어야 하는지까지 정리했습니다.

이 글에서 확인할 것

· 단일 모델과 다중 뷰의 차이

· 설치 없이 5분 안에 확인하는 방법

· DSL 기본 구조와 내보내기

· 저장소에 넣는 운영 방식

· 모델을 믿기 전 확인할 한계

Structurizr란 무엇인가

Structurizr는 C4 모델을 위한 models as code 도구입니다. C4 모델을 만든 Simon Brown이 직접 만들었고, 지금도 C4 모델을 가장 정확하게 따르는 레퍼런스 구현으로 유지되고 있습니다.

핵심은 도구가 아니라 파일입니다. 아키텍처를 Structurizr DSL이라는 텍스트로 적고, 그 파일에서 다이어그램을 파생시킵니다. 파일은 Git에 들어가고, 변경은 diff로 남습니다.

그림은 결과물이고, 모델이 원본입니다. 원본이 텍스트면 리뷰도 버전 관리도 가능해집니다.

모델 하나로 여러 뷰를 만든다

Structurizr에는 두 층이 있습니다. 모델은 요소(person, softwareSystem, container, component)와 그 사이의 관계로 이루어집니다. 뷰는 그 모델을 특정 관점에서 잘라 보여주는 표현입니다.

같은 모델에서 시스템 컨텍스트, 컨테이너, 컴포넌트, 동적, 배포 뷰를 만듭니다. 요소를 하나 추가하면 관련된 모든 뷰에 반영됩니다. 그림마다 손으로 고치던 불일치가 구조적으로 사라지는 이유입니다.

그래서 규칙이 하나 생깁니다. 뷰를 고치는 대신 모델을 고칩니다. 이 규칙 하나가 문서와 실제 구조 사이의 간격을 줄입니다.

설치 없이 확인하기

가장 빠른 방법은 플레이그라운드입니다. 브라우저에서 DSL을 붙여 넣으면 바로 렌더링됩니다. 도구를 설치하지 않고 문법과 뷰의 관계를 익힐 수 있습니다.

로컬에서 돌리려면 Docker 이미지 하나면 충분합니다. 데이터 디렉터리를 마운트하면 첫 실행 때 workspace.dsl이 자동으로 만들어집니다.

docker pull structurizr/structurizr
docker run -it --rm -p 8080:8080 -v PATH:/usr/local/structurizr structurizr/structurizr local

http://localhost:8080을 열면 요약 페이지가 나옵니다. DSL을 저장하고 새로고침하면 그림이 바뀝니다. 레이아웃은 편집기에서 조정하고, 변경은 몇 초 간격으로 자동 저장됩니다.

DSL 기본 구조

DSL은 세 블록으로 시작합니다. workspace, model, views. 사람과 시스템을 정의하고, 관계를 화살표로 잇고, 뷰에서 어떤 범위를 담을지 정합니다.

workspace {
  model {
    u = person "User"
    ss = softwareSystem "Software System"
    u -> ss "Uses"
  }
  views {
    systemContext ss {
      include *
    }
  }
}

person과 softwareSystem은 요소, 화살표는 관계입니다. views 안에서 systemContext 뷰를 선언하고 include *로 전체를 담습니다. 요소를 추가해도 뷰 선언은 그대로 두고 그림만 갱신됩니다.

규모가 커지면 container, component, deployment, dynamic 뷰를 더합니다. 요소 식별자(u, ss)를 명시하면 다른 파일에서도 같은 요소를 참조할 수 있어 모델을 여러 파일로 나눌 수 있습니다.

뷰 내보내기

운영에서는 CLI로 내보냅니다. 위키나 빌드 산출물에 넣을 정적 이미지가 필요할 때 씁니다.

structurizr-cli export -workspace workspace.dsl -format plantuml

형식은 plantuml, c4plantuml, mermaid, websequencediagrams, png, svg, static site 등을 지원합니다. Mermaid로 내보내면 GitHub이나 사내 위키에서 별도 도구 없이 렌더링됩니다.

뷰 답하는 질문
시스템 컨텍스트 이 시스템은 누구와 무엇에 연결되나
컨테이너 배포 단위는 무엇이고 어떻게 통신하나
컴포넌트 컨테이너 내부 책임은 어떻게 나뉘나
동적 한 시나리오에서 호출이 어떤 순서로 흐르나
배포 어떤 환경의 어떤 노드에 올라가나

실무 적용: 저장소에 넣는 방법

가장 단순한 운영은 docs/architecture/workspace.dsl 한 파일입니다. 코드와 같은 저장소에 두면 아키텍처 변경이 코드 변경과 같은 PR에서 리뷰됩니다.

절차는 세 줄이면 됩니다. 모델을 고칩니다 → 검사합니다 → PR에 뷰 이미지를 첨부합니다. 리뷰어는 그림이 아니라 diff를 봅니다. 요소가 언제 왜 늘었는지가 텍스트로 남기 때문입니다.

결정의 배경은 ADR로 분리합니다. DSL은 구조를, ADR은 이유를 담당합니다. 둘을 링크해 두면 6개월 뒤에도 "왜 이렇게 됐는지"를 복원할 수 있습니다.

CI에는 검사와 내보내기를 넣습니다. 모델이 깨지면 빌드가 실패하고, 문서는 항상 최신 상태로 배포됩니다.

한계와 주의

Structurizr는 코드를 읽어 구조를 뽑아내지 않습니다. 모델은 사람이 적습니다. 따라서 코드가 바뀌어도 모델은 자동으로 따라오지 않습니다.

C4의 컴포넌트 뷰는 코드 구조와 가까워지지만, 그것도 자동 추출이 아닙니다. "모델이 코드와 다르다"는 문제는 도구가 아니라 운영 규칙으로 막아야 합니다.

DSL은 학습이 필요하고, 레이아웃은 여전히 손으로 조정합니다. 요소가 수백 개로 늘면 모델을 나누고 이름 규칙을 정하는 비용도 듭니다.

정리하면 Structurizr는 "그림 자동 생성기"가 아니라 구조를 합의하는 문서 형식에 가깝습니다. 그 점을 기대하고 도입하면 만족도가 높습니다.

검증 루틴

1단계. 모델의 요소가 실제 배포 단위와 일치하는지 확인합니다. 컨테이너가 코드의 서비스와 1:1로 대응하지 않으면 뷰를 읽는 사람이 곧바로 혼란을 겪습니다.

2단계. 관계의 방향을 확인합니다. A → B는 "A가 B를 호출한다"는 뜻입니다. 데이터 흐름과 호출 방향이 뒤섞이면 다이어그램이 거짓말을 합니다.

3단계. 변경을 diff로 읽습니다. 요소 추가·삭제가 PR에서 보이면 리뷰가 쉬워집니다. 반대로 그림만 바뀌는 변경은 오히려 경계 신호입니다.

4단계. 검사를 자동화합니다. 문법 오류와 참조 오류를 사람이 눈으로 찾지 않게 만듭니다.

정리

Structurizr의 가치는 예쁜 다이어그램이 아니라, 구조를 텍스트로 남겨 리뷰와 버전 관리의 대상으로 만드는 데 있습니다.

모델 하나에서 여러 뷰를 파생시키면 불일치가 줄고, Git에 두면 변경 이유가 남습니다. 다만 모델은 자동으로 최신이 되지 않으므로, 코드 변경과 같은 PR에서 갱신하는 규율이 필요합니다.

새 프로젝트에 합류했을 때, 아키텍처 리뷰를 준비할 때, 문서가 코드와 어긋나기 시작했다고 느낄 때 한 번 도입을 검토해 볼 만합니다.
