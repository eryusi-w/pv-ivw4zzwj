자동화가 멈추는 순간

자동화는 첫 성공에서 끝났다고 생각하기 쉽습니다. 실제로 시간을 잡아먹는 것은 성공이 아니라 실패한 뒤의 처리입니다. 화면이 로딩 중인지 멈춘 것인지 알 수 없어 5분을 기다리거나, 같은 오류가 나는데도 원인을 고치지 않고 다시 실행합니다.

좋은 자동화는 오래 걸리지 않습니다

좋은 자동화는 오래 걸리지 않습니다. 오래 걸리는 상황을 빨리 실패로 바꿉니다.

문제는 속도가 아니라 재시도

브라우저 자동화에서 정상 실행은 1~2분이면 충분합니다. 그런데 어떤 날은 같은 작업이 18분 걸렸습니다. 원인은 하나였습니다. 선택 상태를 확인하는 방법을 잘못 이해해서, 실제로는 정상 동작하는 단계에서 계속 중단하고 처음부터 다시 실행한 것입니다.

이때 손실은 실행 시간입니다. 같은 원인을 네 번 반복하는 동안 다른 원인을 볼 기회를 잃는 것이 더 큰 손실입니다. 그래서 개선의 방향을 "더 빨리 실행"이 아니라 "같은 실수를 구조적으로 막기"로 바꿨습니다.

자동화를 지키는 네 가지 장치

자동화의 품질은 기능이 아니라 멈추는 방법에서 갈립니다. 워치독, 종료 코드, 2-strike, 이어쓰기 이렇게 네 가지 장치를 곁들이면 사람이 개입할 지점이 눈에 띱니다.

워치독: 응답 없는 프로세스를 끊는다

가장 위험한 상태는 오류가 아니라 응답이 없는 상태입니다. 브라우저 자동화에서는 명령이 영원히 돌아오지 않는 경우가 있습니다. 이때 "10초마다 확인하는 루프"는 소용이 없습니다. 확인 코드 자체가 실행되지 않기 때문입니다.

그래서 응답이 없는 상태를 실패로 바꾸는 것이 첫 번째 장치입니다. 절대 풀리지 않는 타이머를 걸어 두고, 시간이 지나면 진행 상황을 파일에 남긴 뒤 프로세스를 끝냅니다.

const timer = setTimeout(() => {
  saveStatus(status);   // 어디까지 했는지 먼저 남긴다
  process.exit(2);      // 시간 초과 = 환경 문제
}, 90_000);

중요한 것은 상한을 스크립트마다 다르게 두는 것입니다. 진단은 30초, 작성과 발행은 90초, 복구는 180초처럼 단계의 성격에 맞춥니다. 하나의 "5분"으로 묶으면, 빨리 끝나는 작업까지 5분을 기다리게 됩니다.

종료 코드: 다음 행동을 정한다

성공과 실패 두 가지로 나누면 에이전트는 실패를 만났을 때 무엇을 해야 할지 모릅니다. 그래서 종료 코드에 의미를 붙였습니다. 코드가 다음 행동을 결정합니다.

종료 코드 의미 다음 행동
0 성공 다음 단계로 이동
1 검증 실패(데이터) 복구 스크립트 1회 실행
2 시간 초과·정지(환경) 진단 1회, 재실행 금지
3 로그인·권한·상태 이상 즉시 중단, 사람이 판단

이 구분이 있으면 판단이 코드로 옮겨집니다. 에이전트는 "실패했다"가 아니라 "환경 문제이므로 재실행하지 않는다"를 알게 됩니다.

write_post
case $? in
  0) publish_post ;;
  1) repair_code ;;
  2) doctor_once; stop ;;
  3) stop_and_report ;;
esac

2-strike: 같은 원인으로 두 번 실패하지 않기

재시도는 대부분 습관입니다. 실패하면 일단 다시 눌러 봅니다. 하지만 원인이 그대로라면 결과도 마찬가지입니다. 그래서 같은 스크립트가 두 번 실패하면 세 번째 실행을 금지하는 규칙을 넣습니다.

규칙을 문서에만 적으면 지켜지지 않습니다. 실행 직전에 확인하는 코드로 만들어야 합니다. 실패 횟수를 세고, 두 번에 도달하면 원인을 고치기 전까지 실행을 막습니다.

function beforeRun(name) {
  const n = failures.get(name) ?? 0;
  if (n >= 2) throw new Error("2-strike: 원인을 먼저 고치세요");
  failures.set(name, n + 1);
}

이 장치의 효과는 속도가 아니라 방향입니다. 세 번째 실행을 막으면 남는 선택지는 원인을 읽는 것 하나뿐입니다. 로그를 열고, 상태 파일을 보고, 스크립트를 고치게 됩니다.

이어쓰기: 체크포인트와 RESUME

중단 후 처음부터 다시 하는 것도 같은 원인의 반복입니다. 30단계 중 25단계까지 끝냈는데 1단계부터 다시 하면, 실패한 5단계를 만날 때까지 같은 시간을 또 씁니다.

그래서 단계마다 체크포인트를 파일에 남깁니다. 제목, 본문, 코드 블록 개수, 이미지 개수처럼 "다시 하면 안 되는 일"을 기록합니다. 재개할 때는 이 값을 읽어 이미 끝난 단계를 건너뜁니다.

RESUME=1 node write.mjs

재개는 멱등해야 합니다. 이미 끝난 상태에서 다시 실행해도 아무것도 바뀌지 않아야 합니다. 실제로 완성된 글에 재개를 실행했더니 1초 만에 "변경 없음"으로 끝났습니다. 이 성질이 없으면 재개 자체가 중복 입력의 원인이 됩니다.

잠금: 두 실행이 서로를 망치지 않게

자동화를 테스트하다 보면 창을 두 개 띄우게 됩니다. 같은 화면에 두 프로세스가 동시에 키보드를 보내면 결과는 알아보기 힘든 중복 입력입니다. 원인을 찾기도 전에 데이터가 망가집니다.

그래서 스크립트마다 잠금 파일을 둡니다. 두 번째 실행은 즉시 실패합니다. 문제는 강제 종료입니다. 잠금이 남아 있으면 다음 실행이 영원히 막힙니다. 해결은 간단합니다. 잠금 파일에 프로세스 ID를 적고, 그 프로세스가 살아 있는지 확인한 뒤 죽었으면 즉시 회수합니다.

정지 감지: 화면이 아니라 상태를 본다

"화면이 떴다"와 "준비됐다"는 다릅니다. 편집기를 열면 코드 블록이 한 번에 나오지 않습니다. 처음에는 2개가 보이고, 1초 뒤 4개로 늘어납니다. 이때 첫 화면만 보고 판단하면 "코드가 2개뿐"이라고 오판합니다.

그래서 시간이 아니라 변화를 봅니다. 문단 수, 코드 수, 이미지 수 같은 통계를 주기적으로 읽고, 값이 일정 시간(1.2초) 동안 그대로일 때만 로드가 끝난 것으로 봅니다. 고정 대기보다 빠르고, 성급한 판단보다 안전합니다.

측정: 숫자로 확인한 것

장치를 넣은 뒤에는 같은 작업을 다시 재봤습니다. 인상이 아니라 숫자로 비교해야 다음 개선이 보입니다.

작업 이전 이후
고정 대기 합계 18.9초 3.3초
글 작성 1회 측정 불가 20.9초
이어쓰기 1회 처음부터 1.0초
정지 감지 영원히 대기 1.2초에 종료

숫자를 보면 다음 우선순위가 정해집니다. 20.9초 중 이미지 업로드가 7.5초, 코드 입력이 7.6초입니다. 여기서 더 줄이려면 대기 시간이 아니라 업로드 자체를 봐야 한다는 뜻입니다.

정리: 자동화의 완성은 실패 처리

기능을 붙이는 일은 생각보다 어렵지 않습니다. 어려운 것은 실패했을 때 사람 대신 판단하는 일입니다. 워치독은 기다리지 않게 하고, 종료 코드는 다음 행동을 정하며, 2-strike는 같은 실수를 막고, 이어쓰기는 시간을 되돌려줍니다.

이 네 가지를 넣고 나서 작업의 성격이 바뀌었습니다. "언제 끝나지"를 기다리는 대신, "지금 상태가 무엇인지"를 확인하게 됩니다. 자동화가 사람을 기다리게 하지 않는다는 것이 이 글의 결론입니다.

참고: 이 글의 수치는 브라우저 자동화 파이프라인에서 직접 측정한 값입니다. 환경에 따라 달라질 수 있습니다.
