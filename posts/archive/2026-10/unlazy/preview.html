에이전트가 "끝났습니다"라고 말할 때

AI 에이전트에게 큰 작업을 맡기면 마지막이 항상 애매합니다. "완료했습니다"라는 문장은 있는데, 그 문장이 사실인지 확인할 방법이 없습니다. 파일은 절반만 고쳐졌고, 테스트는 실행되지 않았고, 요약은 그럴듯해도 실제와 다를 수 있습니다. 이런 현상을 흔히 게으름이라고 부릅니다. 모델이 일부만 수행하고 끝났다고 보고하기 때문입니다. "끝까지 하세요"라고 프롬프트로 부탁하는 방식은 잘 먹히지 않습니다. 부탁은 검증이 아니기 때문입니다.

완료는 주장이고, 검증은 별개의 작업이다.

unlazy, 완료를 검증로 바꾼다

unlazy는 이 지점을 바로 해결합니다. GitHub에서 4.1k 스타를 받은 에이전트 스킬로, 완료를 주장이 아니라 명령의 종료 코드와 출력으로 바꿉니다. GitHub 스타 4.1k, MIT 라이선스.

unlazy가 푸는 문제

unlazy는 스스로를 "완료 규율(completion discipline)"이라고 소개합니다. 큰 작업을 시작할 때 수용 기준을 먼저 적고, 그 기준을 실행 가능한 검사로 만들고, 돌아온 작업을 다시 검증하고, 증거가 지지하는 것만 보고합니다.

배포 형태는 스킬입니다. Claude Code나 Codex CLI 같은 에이전트에 붙여 /unlazy로 호출합니다. 검사기와 선택 훅은 Node 16 이상만 있으면 되고, 외부 런타임 패키지를 쓰지 않습니다.

핵심은 GATES.md, 원장

핵심 파일은 GATES.md라는 원장입니다. 각 게이트는 체크박스 한 줄과 세 개의 필드로 이루어집니다.

# Gates: pricing behavior

- [ ] G1: pricing fixtures render the expected tiers
  CHECK: node scripts/verify-pricing.mjs
  EXPECT: pricing verification passed
  EVIDENCE: pending

- [ ] G2: checkout integration succeeds from its package
  CHECK: node scripts/verify-checkout.mjs
  EXPECT: checkout verification passed
  CWD: packages/checkout
  EVIDENCE: pending

통과 조건은 두 가지를 동시에 만족해야 합니다. 프로세스가 0으로 끝나고, EXPECT 문자열이 합쳐진 출력에 포함되어야 합니다. "테스트 통과"라는 문장을 사람이 읽고 판단하는 대신, 그 문장이 실제로 출력됐는지 기계적으로 봅니다. CWD를 적으면 그 디렉터리에서 명령이 실행됩니다.

증거, 자동으로 채워집니다

EVIDENCE는 자동으로 채워집니다. CHECK, EXPECT, CWD 정의의 SHA-256 다이제스트로 시작하고, 종료 코드와 성공 출력의 지문이 뒤따릅니다. 정의가 바뀌면 기존 증거는 오래된 것(stale)으로 취급되어 게이트가 다시 미달이 됩니다.

승인과 실행의 분리

CHECK는 셸 코드입니다. 그래서 unlazy는 처음 보는 게이트를 곧바로 실행하지 않습니다. 승인 기록이 없는 명령은 실행 계획만 보여줍니다. 해석된 명령, 기대 출력, 작업 디렉터리, 셸, PATH까지 출력합니다.

# 실행하지 않고 형식만 본다 (유일하게 항상 비실행)
node scripts/gate-check.mjs --status GATES.md

# 처음 보는 명령은 실행 전에 해석 결과를 보여준다
node scripts/gate-check.mjs GATES.md

# 내용을 읽고 승인한 뒤 실행
node scripts/gate-check.mjs --approve GATES.md

# 이미 통과한 게이트까지 다시 실행
node scripts/gate-check.mjs --reverify GATES.md
모드 명령 실행 쓰는 상황
--status 항상 안 함 형식·정의 변경 확인
기본 실행 승인 전에는 안 함 첫 검토, 승인 후 실행
--approve 함 검토를 마친 원장 실행
--reverify 완료 포함 전부 상위 작업의 재검증

주의할 점이 있습니다. 기본 실행을 영구적인 드라이런으로 오해하면 안 됩니다. 정확한 게이트가 한 번 승인되면, 기본 실행은 그 명령을 실제로 돕니다. "미리 보겠지"라고 가정하는 순간 승인의 의미가 사라집니다.

증거가 성립하는 조건

증거는 문장이 아니라 결속(binding)입니다. 자동 증거는 정의 다이제스트로 시작해서 종료 코드와 성공 출력 지문을 담습니다. 같은 정의에서 나온 기록인지 기계적으로 구분할 수 있습니다.

다만 이 결속은 원장 조작까지 막지는 못합니다. 원장을 고칠 수 있는 사람은 그럴듯한 증거도 만들 수 있습니다. unlazy 문서가 직접 인정하는 한계이며, 이 장치가 잡는 것은 구조적 드리프트입니다.

출력 크기 제한도 있습니다. 캡처된 출력과 EXPECT 비교에 쓰는 문자열이 각각 1MiB를 넘으면, 잘라서 성공으로 만들지 않습니다. 큰 로그를 성공으로 오인하는 경로를 없앤 것입니다. 기존에 사람이 손으로 적은 증거도 계속 호환됩니다.

같은 셸, 같은 도구 체인

같은 검사도 어떤 셸에서 돌렸는지에 따라 결과가 달라집니다. 특히 Windows에서 Git Bash로 실행한 검사는 grep, tail 같은 도구를 볼 수 있지만 PowerShell에서는 볼 수 없습니다.

--shell 옵션은 인터프리터를 바꾸지만, 프로그램을 설치하지는 않습니다. 그래서 이식 가능한 예시는 저장소가 소유한 Node 스크립트를 호출합니다. 부모가 자식의 작업을 재검증할 때도 같은 셸과 도구 체인을 써야 합니다. 셸이나 PATH가 다르면 그것 자체가 해결해야 할 실패입니다.

승인은 격리가 아니다

승인 기록은 기본적으로 ~/.unlazy/approved에 저장됩니다. 저장소 밖의 소유자 전용 디렉터리여야 하고, 심볼릭 링크나 공유 파일은 거부됩니다. 기록은 원장 경로와 게이트, CHECK와 EXPECT, CWD와 셸, 타임아웃, PATH까지 묶입니다. 어느 하나라도 바뀌면 다시 승인해야 합니다.

그러나 승인은 동의이지 격리가 아닙니다. 검사는 주변 파일 시스템과 환경 변수, 자격 증명, 네트워크에 그대로 접근합니다. unlazy는 "이 명령을 실행해도 된다"를 기록할 뿐, "이 명령이 할 수 있는 일"을 제한하지 않습니다. 승인은 호출된 스크립트나 의존성까지 해시하지도 않습니다. 그래서 의존성이 바뀌면 --reverify로 다시 돌려야 합니다.

깊이 트리와 병렬 작업

큰 작업은 .unlazy// 아래에 PLAN, GATES, leaf 원장으로 나눕니다. leaf는 WAITING, READY, IN-FLIGHT, VERIFIED, ABANDONED 상태를 갖고, 브랜치는 OPEN, VERIFIED, ABANDONED를 씁니다.

node scripts/gate-check.mjs --scope api --leaf leaf-1.2.1 --claim
node scripts/gate-check.mjs --scope api --jobs 4
npm test

병렬 실행에는 조건이 있습니다. 각 leaf가 겹치지 않는 OWNS 경로를 선언하고 임차(lease)를 얻어야 같이 돌 수 있습니다. 임차는 조정 장치이지 쓰기 격리가 아니므로, 충돌하는 작업은 워크트리를 분리해야 합니다. 기본은 순차 실행이고 --jobs는 1부터 64까지 선택합니다.

포기(abandon)도 정식 상태입니다. 이유를 적어야 하고, 포기한 게이트는 상위 작업을 완료로 승격시키지 못합니다. "일단 접고 성공이라고 보고"하는 경로를 막아 둔 것입니다.

도입 전 확인할 것

  1. 버전: 현재 소스는 2.1.0을 목표로 하지만, 태그된 릴리스로 확인되지는 않습니다. 재현 가능한 설치를 위해서는 커밋을 고정해야 합니다.
  2. 연구 인용의 범위: unlazy의 README는 연구가 실패 모드를 뒷받침한다고 말하면서, unlazy가 고정된 개선을 만든다는 증명은 아니라고 스스로 밝힙니다.

정리하면 이렇습니다. 에이전트의 "완료했습니다"를 믿는 대신, 완료를 확인하는 명령을 남기는 쪽이 장기갑니다. unlazy는 그 습관을 원장과 CLI로 고정하는 도구이며, 무엇을 검사할지는 여전히 사람이 정해야 합니다.
