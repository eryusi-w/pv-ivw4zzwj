문제 제기

AI 코딩 에이전트가 일하는 방식은 사람과 다릅니다. 사람은 저장소를 통째로 clone하고 몇 시간을 작업한 뒤 한 번 push하죠. 에이전트는 짧은 작업 수천 개가 같은 브랜치에 몇 초 간격으로 land하려 합니다.

이 규모에서는 풀 clone, 머지 큐, 클라이언트 측 이력 탐색이 병목이 됩니다. Git 자체가 나빠진 게 아니라, Git이 사람의 작업 리듬에 맞춰 설계됐기 때문입니다.

수천 개의 단명 작업이 같은 브랜치에 동시에 land하려 할 때, Git은 병목이 됩니다.

무엇인가

git-ai(feder-cr/git-ai)는 이 문제를 정면으로 다루는 오픈소스 버전 관리 시스템입니다. GitHub 별 1천 개, 포크 104개, 현재 버전 0.4.2, MIT 라이선스입니다. 코드베이스는 Go로 작성돼 있습니다.

배경이 흥미롭습니다. Anthropic이 코딩 에이전트용 버전 관리 시스템 Scion을 만들고 "소스 컨트롤 재설계"라는 글로 설계를 공개했습니다. Scion은 Anthropic 내부용이라 외부에서 쓸 수 없고, git-ai는 그 공개된 설계를 누구나 돌릴 수 있게 독립 구현한 프로젝트입니다. Anthropic과 제휴 관계는 없습니다.

핵심 원칙은 벤더 중립입니다. 서버가 언어 모델을 호출하지 않고, 모든 AI 기능은 어떤 프로바이더와도 — 아니면 아무것도 없이도 — 동작합니다.

이름 정리 — 저장소 안에서는 확장 기능을 "Graft"라고 부릅니다. [graft] 설정 섹션, graft CLI, internal/graft가 그 흔적입니다.

소스 컨트롤을 API로

git-ai의 출발점은 하나입니다. 클라이언트가 항상 온라인 상태를 유지하고, 필요한 것만 가져가게 만들면 병목 대부분이 사라집니다. blame, 경로 이력, ancestry 같은 질문은 서버가 계산해서 캐시합니다. 코드 검색도 인덱스 없이 서버에서 돌립니다.

  • 항상 온라인 클라이언트 — graft clone과 graft sparse가 요청한 경로만 구체화합니다.
  • 소스 컨트롤이 API — blame·이력·검색이 서버 측 파생 데이터로 계산되고 커밋당 한 번만 캐시됩니다.
  • 머지 큐 없는 랜딩 — UserLand가 변경을 현재 tip에 리베이스하고 compare-and-swap으로 반영합니다. 한 브랜치의 동시 land는 참조 업데이트 하나로 묶입니다.
  • 체인지셋 로그 — 수용된 모든 참조 업데이트가 조밀하고 순서 있는 로그에 기록되고, 클라이언트가 실시간으로 watch합니다.

밑바닥에는 평범한 Git 저장소가 깔려 있습니다. 클라이언트의 로컬 Git 저장소는 어느 노드든 재구축할 수 있는 캐시 역할입니다.

충돌 해결과 검증

land가 충돌하면 어떻게 할지가 이 시스템의 핵심 질문입니다. git-ai는 리졸버를 사용자가 고르게 합니다. 아무 LLM 프로바이더나 쓸 수 있고, 결정론적 도구를 쓸 수도, 쓰지 않을 수도 있습니다. 이 프로토콜은 버전 관리되고 벤더 중립입니다.

모델의 해결안은 어디까지나 제안입니다. 사용자가 설정한 verify.command가 실제로 land될 트리에서 통과할 때만 스스로 land하고, 아니면 에이전트에게 충돌 패키지와 제안을 넘깁니다. 결정론적 규칙은 이 조건 없이 설정대로 검증됩니다.

land 이후에도 장치가 있습니다. graft-verify가 tip을 테스트하고, 실패를 이분 탐색해 망가뜨린 변경을 찾아 revert합니다. 에이전트들은 체인지셋 스트림을 구독해 자기 컴포넌트에 중요한 변화만 보고하고, Slack으로도 알릴 수 있습니다.

저장소 구조

저장 상태는 데이터베이스와 오브젝트 스토리지에 나뉘어 있습니다. 변경 하나가 쓰기 전 로그(WAL)의 체인지셋이고, 참조마다 compare-and-swap이 붙습니다. 팩은 콘텐츠 주소 방식으로 오브젝트 스토리지(file, S3, GCS, Azure)에 둡니다.

구성 요소 역할
SQLite / PostgreSQL 체인지셋 WAL, 참조, 체인지로그, 리뷰
오브젝트 스토리지 콘텐츠 주소 팩 (file, S3, GCS, Azure)
로컬 Git 저장소 캐시 — 어느 노드든 재구축 가능
서버 노드 캐시이므로 노드를 늘려 스케일 아웃

에이전트 보안도 일급 기능입니다. 에이전트별 토큰, RPC 허용 목록, 브랜치 정책이 각 에이전트가 할 수 있는 일을 결정합니다. 리뷰도 에이전트 친화적이라, 코멘트만 바뀐 변경은 로직 변경보다 적은 승인을 요구할 수 있습니다.

설치와 첫 실행

Linux 또는 macOS가 필요하고, Go 1.26, C 툴체인, Meson, Ninja가 깔려 있어야 합니다. 빌드는 번들된 Git을 컴파일하기 때문입니다. Windows는 공식 지원 대상이 아닙니다.

git clone https://github.com/feder-cr/git-ai.git
cd git-ai
make build                    # server, CLI, tools → _build/bin

# 서버 + 캐시 데몬 + 에이전트 2개 + land까지 한 번에
examples/graft/quickstart.sh

./_build/bin/graft            # CLI

자체 서버를 띄우려면 examples/graft/config.toml을 고쳐 _build/bin/gitaly serve config.toml로 시작합니다. 저장소 상태를 데이터베이스와 오브젝트 스토리지로 옮기려면 [graft.storage] 섹션을 추가하고, shadow 모드로 저장소를 가져온 뒤 authoritative로 전환합니다.

벤치마크

README는 50개 에이전트가 한 브랜치에 변경 5개씩, 총 250개를 land하는 시나리오를 공개합니다. 20%는 의도적으로 충돌을 일으킵니다. "classic"은 배칭을 끈 같은 서버로, 에이전트마다 리베이스와 재시도를 최대 20회까지 반복하는 방식입니다.

50 에이전트, 250 변경 classic gitai
land된 변경 100~106 200
변경당 시도 횟수 26.5~28.7 1.0
분당 land 264~385 1,487~1,944
p99 지연 4.4~5.2초 1.9~2.7초

gitai가 land하지 못한 50개는 계획된 충돌로, 리졸버 없이 에이전트에게 되돌아갑니다. 결정론적 리졸버(resolve.toml)를 붙이면 충돌이 모두 해결돼 250개 전부가 land됩니다. 16코어 한 대에서 측정한 값이고, 0.4.0 기준으로 재측정되지는 않았습니다.

한계와 주의

솔직한 상태 표기가 좋습니다. 현재 버전은 0.4.2이고, 구현된 기능은 단위·E2E·멀티노드·크래시·퍼즈 테스트로 덮여 있지만 모든 테스트가 한 대의 머신에서 돌아갑니다. 여러 노드가 하나의 데이터베이스와 버킷을 공유하는 구성까지만 검증됐고, 별도 머신의 노드는 테스트되지 않았습니다.

S3, GCS, Azure 버킷도 테스트되지 않았고(file과 인메모리만 검증), 팩 GC는 있지만 기본으로 꺼져 있습니다(gc = "auto" 또는 graft storage gc). 1.0 이전이라 인터페이스는 아직 바뀔 수 있습니다. 에이전트 수백 개 규모의 실서비스에 바로 올리기보다, quickstart로 구조를 확인한 뒤 도입 범위를 정하는 게 안전합니다.

도입 전 체크리스트

확인할 것 4가지

✓ 환경 — Linux/macOS, Go 1.26, C 툴체인, Meson, Ninja 필요

✓ 스토리지 — SQLite/PG + 오브젝트 스토리지 구성을 shadow 모드로 먼저

✓ 리졸버 — verify.command 설정 여부와 충돌 정책 결정

✓ 한계 — 멀티머신 미검증, S3/GCS/Azure 미검증, 1.0 전 인터페이스 변경 가능

정리

git-ai는 "Git을 더 빠르게"가 아니라 "에이전트 수천 개가 동시에 일하는 세계의 소스 컨트롤"을 다시 설계한 프로젝트입니다. 서버 중심, 항상 온라인, CAS 랜딩, 체인지셋 로그까지 Scion의 공개 설계를 MIT로 구현했고, 서버가 모델을 부르지 않는 벤더 중립 설계가 이 프로젝트의 성격을 가장 잘 보여 줍니다.

오늘 해 볼 일은 examples/graft/quickstart.sh 하나입니다. 서버와 캐시, 에이전트 두 개, land 한 번이 임시 디렉터리에서 돌아가는 걸 보면 이 시스템이 실제로 어떻게 움직이는지 감이 잡힙니다.
