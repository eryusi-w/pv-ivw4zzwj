AI 코딩 도구, 무엇이 달라졌나

AI 코딩 도구의 성격이 바뀌었습니다. 예전 도구가 커서 다음 줄을 예측하는 자동완성이었다면, 지금의 CLI 도구는 저장소를 읽고 파일을 고치고 테스트까지 실행합니다. 비교의 기준도 "자동완성이 얼마나 정확한가"에서 "얼마나 안전하게 일을 끝내는가"로 옮겨갔습니다.

이 글은 Claude Code와 GitHub Copilot CLI를 축으로 도구를 고르는 기준과 첫 실행 절차를 정리합니다. 설치 명령은 공식 문서에 있는 것만 적었고, 직접 확인하지 못한 기능은 넣지 않았습니다.

도구를 나누는 세 가지 축

도구를 고를 때 실제로 갈리는 지점은 세 가지입니다. 코드가 어디서 실행되는지, 어디까지 권한을 주는지, 돈이 어떻게 나가는지입니다. 이 세 축을 먼저 정하면 브랜드 비교는 그다음 문제가 됩니다.

축터미널형에디터형
실행 단위명령과 작업 단위파일과 커서 단위
권한 범위파일 수정·명령 실행제안 후 사람이 적용
강점여러 파일 리팩터링한 파일 집중 편집
요금구독 또는 API 사용량대개 구독에 포함

표에서 가장 중요한 줄은 권한 범위입니다. 터미널형은 도구가 직접 파일을 쓰고 셸 명령을 실행하므로, 잘못된 지시 하나가 저장소 밖까지 영향을 줄 수 있습니다. 에디터형은 적용 전에 사람이 확인하는 단계가 남아 있어 사고 반경이 좁습니다.

터미널형과 에디터형의 차이

터미널형은 작업을 위임하는 방식에 가깝습니다. "이 테스트가 실패하는 원인을 찾아 고쳐줘"처럼 결과 중심으로 지시하면, 도구가 파일을 찾고 고치고 다시 실행하는 과정을 스스로 반복합니다. 사람은 중간 과정을 로그로 확인하고 마지막 diff를 검토합니다.

에디터형은 판단을 나눠 갖는 방식입니다. 모델이 제안을 만들고 사람이 수락하는 흐름이라 통제가 쉽지만, 여러 파일에 걸친 변경은 사람이 계속 조율해야 합니다. 파일 열 개를 넘나드는 작업이라면 터미널형이, 한 함수의 구현을 다듬는 일이라면 에디터형이 편합니다.

둘을 동시에 쓰는 구성도 자연스럽습니다. 큰 변경은 터미널에서 위임하고, 마지막 다듬기는 편집기에서 직접 하는 식입니다.

Claude Code 설치와 첫 실행

Claude Code는 두 가지 경로로 설치합니다. Node.js가 이미 있으면 npm 패키지가 간단하고, 없으면 네이티브 설치 프로그램을 쓰면 됩니다. npm 패키지는 Node.js 22 이상을 요구하지만, 실행 자체는 플랫폼별 네이티브 바이너리를 내려받아 동작합니다.

# 1) npm 설치 (Node.js 22 이상)
npm install -g @anthropic-ai/claude-code

# 2) Windows PowerShell 네이티브 설치
irm https://claude.ai/install.ps1 | iex

# 3) 업데이트는 latest 태그로 명시한다
npm install -g @anthropic-ai/claude-code@latest

# 4) 프로젝트 폴더에서 실행
cd D:\work\my-project
claude

설치 후에는 새 터미널을 열고 버전을 확인합니다. claude --version이 숫자를 출력하면 정상입니다. 설치는 되었는데 명령을 찾지 못한다면 PATH 반영 전에 실행한 경우가 대부분이라, 터미널을 다시 열면 해결됩니다.

GitHub Copilot CLI 설치와 첫 실행

Copilot CLI는 GitHub Copilot 구독이 전제입니다. 설치 경로는 npm, winget, Homebrew, 설치 스크립트로 나뉘고, 어느 쪽이든 첫 실행 때 인증만 하면 같은 방식으로 씁니다. Windows에서 PowerShell 6 이상이 필요한 점은 미리 확인해 두는 편이 좋습니다.

# npm (Node.js 22 이상)
npm install -g @github/copilot

# Windows
winget install GitHub.Copilot

# macOS / Linux
brew install copilot-cli

# 실행 후 /login 으로 인증
copilot

# 한 번만 물어보고 끝내기
copilot -p "이 저장소의 빌드 명령을 알려줘"

-p 플래그는 대화형 세션을 열지 않고 한 번만 응답을 받는 용도입니다. 스크립트나 파이프라인에서 짧은 질문을 던질 때 유용하고, 긴 작업은 copilot으로 세션을 열어 진행 상황을 보면서 처리하는 편이 안전합니다.

첫 작업은 어떻게 지시하나

첫 실행에서 가장 많이 하는 실수는 "버그 고쳐줘"처럼 범위를 비워 두는 것입니다. 도구는 빈칸을 추측으로 채우고, 그 추측이 맞을 이유는 없습니다. 지시를 짧게 나누는 편이 결과가 좋습니다.

# 범위가 없는 지시
"버그 고쳐줘"

# 범위, 순서, 금지사항을 함께 준 지시
"src/auth/session.ts 의 refresh 만료 처리에서 401이 반복되는 원인을 찾아줘.
 실패를 재현하는 테스트를 먼저 추가하고, 그 다음 최소 수정으로 고쳐줘.
 커밋과 push는 하지 마."

세 문장이면 충분합니다. 어디를 볼지, 어떤 순서로 할지, 하지 말아야 할 일이 무엇인지가 들어 있으면 도구는 탐색 범위를 좁힙니다. 반대로 "최적화해줘"처럼 기준이 없는 요청은 측정 없는 변경을 낳습니다.

결과를 검토하는 루틴

자동화의 품질은 검토 루틴에서 결정됩니다. 도구가 "완료했다"고 말한 것과 실제로 동작하는 것은 다른 문제입니다. 그래서 매번 같은 순서로 확인합니다.

  • 변경 범위: 예상하지 못한 파일이 수정됐는지 diff로 확인합니다.
  • 재현 테스트: 수정 전 실패하고 수정 후 통과하는 테스트가 있는지 봅니다.
  • 실행 로그: 테스트 명령이 실제로 돌았는지, 아니면 실행 없이 통과를 주장했는지 확인합니다.
  • 부작용: 설정 파일, 의존성, 마이그레이션이 함께 바뀌지 않았는지 봅니다.

이 네 가지를 습관으로 만들면 검토 시간은 몇 분으로 줄고, 되돌리기 어려운 사고는 대부분 걸러집니다.

비용과 한도 관리

터미널형 도구는 토큰을 많이 쓰는 방향으로 진화했습니다. 저장소를 읽고, 실패 로그를 다시 읽고, 수정한 파일을 또 읽기 때문입니다. 같은 작업을 반복하면 비용도 함께 늘어납니다.

관리 방법은 세 가지로 정리됩니다. 세션을 작업 단위로 끊어 컨텍스트를 비우고, 큰 탐색은 검색 명령으로 먼저 좁히고, 반복되는 작업은 스크립트로 빼서 모델 호출을 줄입니다. 구독형 요금제를 쓴다면 사용량보다 한도 소진 시점을 보고 작업 순서를 정하는 편이 현실적입니다.

흔한 실패와 주의할 점

가장 위험한 설정은 권한 자동 승인입니다. 테스트와 빌드는 자동으로 돌려도 되지만, 파일 삭제나 외부 전송까지 승인해 두면 되돌릴 수 없는 사고가 납니다. 작업 디렉터리를 저장소 안으로 제한하고, 파괴적인 명령은 매번 확인하는 편이 낫습니다.

두 번째는 오래된 문서를 믿는 경우입니다. 패키지 이름과 설치 명령은 판올림 과정에서 바뀝니다. 블로그 글보다 공식 문서의 설치 페이지를 먼저 확인하고, 명령이 동작하지 않으면 버전 차이를 의심해야 합니다.

세 번째는 검증 없는 신뢰입니다. 도구가 만든 코드는 실행해 보기 전까지 초안입니다. 테스트가 없는 저장소라면, 도구를 쓰기 전에 테스트를 먼저 만드는 순서가 안전합니다.

정리: 나에게 맞는 도구 고르기

여러 파일을 넘나드는 작업이 많고 결과만 확인하면 된다면 터미널형이 맞습니다. 코드를 한 줄씩 통제하고 싶다면 에디터형이 맞습니다. 판단 기준은 유행이 아니라 권한 범위와 검토 비용입니다.

처음 시작한다면 저장소 하나를 정해 작은 작업부터 맡겨 보십시오. 설치, 인증, 첫 지시, diff 검토까지 한 바퀴 돌아보면 어떤 도구가 맞는지 대개 그 자리에서 판단이 섭니다.
