문제 제기: "이런 부품 하나 만들어 줘"가 어려운 이유

CAD로 부품을 만드는 일은 도구를 배우는 것부터 시작입니다. 솔리드Works든 Fusion이든 FreeCAD든, 치수를 입력하고 스케치하고 피처를 쌓는 데 익숙해지기까지 시간이 걸립니다. AI에게 "브라켓 하나 그려 줘"라고 해도, 결과물이 STEP 파일로 떨어지지 않으면 실물로 이어지지 않습니다.

그런데 요즘 에이전트는 이미 코드로 모델을 만들 수 있습니다. 문제는 그 코드가 CAD 형식으로 번역되는 다리가 없었다는 점입니다.

말로 시키면 Python 스크립트가 되고, 그 스크립트가 STEP·GLB·STL·3MF 파일이 되는 도구가 text-to-cad입니다.

무엇인가: text-to-cad

earthtojake/text-to-cad는 AI 에이전트에게 로컬 CAD 작업 흐름을 주는 플러그인·스킬 모음입니다. GitHub 별 2.6만 개, 라이선스는 MIT입니다.

핵심 아이디어는 단순합니다. 에이전트가 부품을 Python 스크립트로 쓰고, 그 스크립트를 실행하면 로컬 서버가 3D 모델을 STEP, GLB, STL, 3MF로보냅니다. 도면 생성, 제작 가능성 검사, 3D 프린팅·판금·CNC 서비스 연동까지 같은 흐름에서 처리합니다.

Claude Code, Codex, Cursor, Gemini, Grok 등 플러그인이나 skills 프레임워크를 지원하는 에이전트라면 대부분 붙습니다.

동작 원리: build123d에서 XBF까지

파이프라인은 세 단계입니다.

  1. 에이전트가 모델을 build123d로 된 Python 스크립트로 작성합니다. build123d는 Open CASCADE 위에서 돌아가는 CAD용 파이썬 라이브러리입니다.
  2. 스크립트를 실행(python model.py)하면 text-to-cad 서버가 .xbf 문서(부품·이름·색·재질·조인트)를 만들고, 스크립트가 선언한 STEP·GLB·STL·3MF를 출력합니다. 서버는 모델 작업을 메모리에 유지해 수정 시 바뀐 부분만 다시 만듭니다.
  3. CAD 뷰어가 에이전트 앱이나 브라우저에서 모델을 보여 주고, 리빌드할 때마다 따라갑니다.
자연어 요청 → build123d 스크립트 → .xbf + STEP/GLB/STL/3MF → CAD 뷰어

설치: 스크립트 한 줄

macOS·Linux는 curl 한 줄, Windows는 PowerShell 명령입니다. uv가 없으면 같이 설치하고, 컴퓨터의 에이전트 앱마다 알맞은 방식(플러그인 또는 스킬)으로 심어 줍니다.

# macOS · Linux
curl -fsSL https://texttocad.dev/install.sh | sh

# Windows PowerShell
irm https://www.texttocad.dev/install.ps1 | iex

# 수동으로는 PyPI 패키지
pip install cad-server

설치 후에는 에이전트에게 "이런 부품 만들어 줘"라고 말하면 됩니다. 에이전트가 스크립트를 쓰고, 실행하고, 뷰어에 띄웁니다. 업데이트는 같은 스크립트를 다시 실행하면 됩니다.

스킬 목록: CAD 바깥까지

CAD 스킬 하나만 있는 게 아닙니다. 로봇 기술자, 도면가, 제작 담당자까지 덮는 스킬이 12개 있습니다.

스킬 하는 일
cad 자연어·이미지 요청으로 모델 작성, XBF 문서와 STEP·STL·3MF·GLB 출력
step.parts 볼트·베어링·모터·커넥터 같은 기성 STEP 부품 찾기
engineering-drawing 부품에서 치수 들어간 도면 PDF — 뷰, 숨은선, 치수선, 구멍 표기, 타이틀 블록
dfm / dfam-check 판금·CNC·사출 성형 검토(측정 근거 포함), 프린트 가능성 측정(벽 두께·오버행·서포트)
gcode / bambu-labs OrcaSlicer로 G-code 슬라이싱, Bambu 프린터로 전송
urdf / srdf / sdf 로봇 구조 파일(URDF), MoveIt 계획 그룹(SRDF), 시뮬레이터 모델(SDF)
sendcutsend SendCutSend 업로드 전 DXF·STEP 파일 점검

URDF와 로봇 구조 파일까지

재미있는 확장은 로봇 쪽입니다. urdf 스킬은 링크·조인트·관성·메시를 담은 로봇 구조 파일(URDF)을 쓰고, srdf는 거기에 MoveIt 계획 그룹과 엔드 이펙터·충돌 규칙을 얹습니다. sdf는 Gazebo 같은 시뮬레이터용 모델과 월드를 만듭니다.

즉 "모터 브라켓을 만들어 줘"에서 끝나지 않고, 그 브라켓이 로봇 팔의 링크가 되고 시뮬레이터에서 움직이는 것까지 한 흐름으로 갑니다. 하드웨어를 만지는 사람이 아니라 소프트웨어 쪽에서 로봇을 설계하는 진입 장벽을 낮추는 셈입니다.

제작 가능성 검사는 사람 몫이 아니다

모델이 예쁘게 나와도 실제로 만들 수 없으면 의미가 없습니다. dfm 스킬은 판금·CNC·사출 성형 각각의 규칙을 적용해 측정값과 근거 규칙을 함께 보고합니다. dfam-check는 메시 기준으로 벽 두께, 오버행, 서포트 부피, 빌드 방향을 재서 프린터별로 프린트 가능성을 봅니다.

도면이 필요하면 engineering-drawing이 부품에서 PDF 도면을 뽑습니다. 뷰, 숨은선, 치수선, 구멍 콜아웃, 타이틀 블록까지 포함입니다.

한계와 주의

먼저 텔레메트리입니다. 기본으로 사용 통계와 크래시 리포트가 전송되는데, 무작위 ID가 붙고 파일·경로·프롬프트는 포함되지 않는다고 README가 밝힙니다. 그래도 끄고 싶다면 프라이버시 정책을 확인하세요.

둘째, "말로 CAD를 만든다"는 것의 한계입니다. 복잡한 조립품의 공차, 표준 부품과의 정합성, 제조사의 실제 제약은 여전히 사람이 봐야 합니다. DFM 검사가 있어도 최종 승인은 엔지니어의 몫이죠. 셋째, MIT 라이선스지만 생성되는 STEP 파일의 사용 권리는 모델·재질 라이선스와 별개로 확인이 필요합니다.

도입 전 체크리스트

확인할 것 4가지

✓ 에이전트 호환 — 쓰는 에이전트가 플러그인 또는 skills 프레임워크를 지원하는지

✓ 출력 형식 — STEP·GLB·STL·3MF 중 필요한 제작 파이프라인이 받는 형식인지

✓ 검증 — DFM·도면 스킬로 제작 가능성을 먼저 확인하는 절차

✓ 텔레메트리 — 기본 전송되는 사용 통계·크래시 리포트를 끄는 방법 확인

정리

text-to-cad는 "말로 부품을 주문하면 CAD 파일이 나오는" 것을 현실로 만든 프로젝트입니다. build123d 스크립트가 STEP·GLB·STL·3MF로 번역되고, 도면·DFM·로봇 파일까지 같은 생태계에서 처리합니다.

오늘 해 볼 일은 간단합니다. 설치 스크립트를 실행하고 에이전트에게 "30mm 브라켓 하나 만들어 줘"라고 시켜 보세요. 뷰어에 3D가 뜨는 순간, 이 도구가 어디까지 왔는지 체감됩니다.
