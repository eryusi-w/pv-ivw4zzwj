문제 제기

AI 에이전트에게 날짜 선택기를 만들어 달라고 하면 이렇게 됩니다. 라이브러리를 설치하거나, 달력과 선택기를 통째로 손으로 짭니다. 335줄짜리 코드가 나옵니다. 동작은 하는데, 이미 저장소에 Input 컴포넌트가 있고 브라우저에는 type="date"가 있는데도요.

에이전트는 요청받은 일을 하면서 주변까지 손봅니다. 추상화를 하나 더 넣고, 미래를 대비한 계층을 만들고, 설정 파일을 추가합니다. 결과는 동작하지만 읽기 어려운 코드입니다.

가장 좋은 코드는, 쓰지 않은 코드입니다.

무엇인가

ponytail(DietrichGebert/ponytail)은 AI 에이전트가 방 안에서 제일 게으른 시니어 개발자처럼 판단하게 만드는 스킬입니다. GitHub 별 18만 5천 개, 포크 1만 개, MIT 라이선스입니다. 본질은 프롬프트 하나입니다 — skills/ponytail/SKILL.md 한 파일이 전부고, 나머지는 그걸 각 에이전트에 싣는 어댑터입니다.

Claude Code, Codex, Cursor, Windsurf, Cline, Copilot, Kiro, OpenCode, Gemini, Devin CLI 등 20개 에이전트를 지원합니다. 이 글의 제목처럼 "게으른 시니어"가 핵심인데, 여기서 게으름은 대충 함이 아니라 요구를 만족하는 가장 작은 변경을 고르는 태도입니다.

규칙의 본질 — "가장 적은 토큰"이 목표가 아닙니다. 작업에 필요한 것만 쓰고, 검증·에러 처리·보안·접근성은 절대 깎지 않습니다. 코드가 작게 나오는 건 필요해서지, 골프를 쳐서가 아닙니다. 비용과 지연 감소는 부수 효과입니다.

동작 원리: 사다리

코드를 쓰기 전에 멈추고 사다리를 올라갑니다. 문제를 이해한 뒤에 사다리를 타는 겁니다. 해법에 게으르되, 읽는 데는 게으르지 않습니다. 변경이 건드리는 코드를 읽고 실제 흐름을 따라간 다음 사다리를 고릅니다.

단계 질문
1 이게 존재할 필요가 있는가
2 이 코드베이스에 이미 있는가
3 표준 라이브러리가 하는가
4 네이티브 플랫폼 기능인가
5 설치된 의존성이 하는가
6 한 줄로 되나
7 그때서야 동작하는 최소 코드 + 작은 테스트 하나

처음 성립하는 단계에서 멈춥니다. 앞의 사례가 이걸 보여 줍니다. 손으로 만든 달력 335줄 대신, 저장소의 Input과 브라우저의 type="date"를 합쳐 10줄짜리 파일 하나로 끝냈습니다.

분기가 있거나, 루프나 파서, 돈이나 보안이 걸린 로직은 작은 테스트 하나를 남깁니다. 모든 답변은 "뭘 건너뛰었고 뭘 확인하지 않았는지, 알아야 할 리스크"로 끝납니다.

설치

Claude Code에서는 플러그인 마켓플레이스로 설치합니다. Codex는 플러그인 명령이 따로 있고, 다른 에이전트는 AGENTS.md를 프로젝트에 복사하거나 SKILL.md를 스킬로 싣는 방식입니다.

# Claude Code
/plugin marketplace add DietrichGebert/ponytail
/plugin install ponytail@ponytail

# Codex
codex plugin marketplace add DietrichGebert/ponytail
codex plugin add ponytail@ponytail
# 이후 Codex에서 /hooks를 열어 라이프사이클 훅 두 개를 신뢰

설치하면 세션마다 켜져 있고, 강도는 /ponytail lite|full|ultra|off로 조절합니다. 인자 없이 치면 꺼져 있을 때 기본 강도로 켜지고, 켜져 있으면 현재 단계를 알려 줍니다.

명령어

명령 하는 일
/ponytail-review diff가 아니라 변경이 건드리는 코드까지 읽고 리뷰 — 버그, 보안, 실제 부하, 테스트 없는 위험 코드, 지울 것
/ponytail-audit 저장소 전체를 매핑하고 발견 사항을 "먼저 고칠 것" 순으로 랭킹
/ponytail-debt 미뤄 둔 shortcut: 주석을 장부로 수집 — "나중에"가 "영영"이 되지 않게
/ponytail-gain 벤치마크의 실측 성과판 표시
/ponytail band Claude Code 전용: 프롬프트 위 비용·토큰·시간·재사용률 밴드 표시

밴드는 Claude Code 2.1.290 이상에서 터미널이나 데스크톱 앱에만 뜹니다. VS Code 채팅 패널, 클라우드 세션, claude -p에는 표시되지 않습니다. Board는 로컬 페이지를 열어 프로젝트별 비용·시간·토큰과 세션별 테스트 통과 여부를 보여 주고, 기본적으로 모든 데이터는 ~/.config/ponytail/band/에 머뭅니다.

벤치마크 읽는 법

Ponytail 5는 처음부터 다시 만들었습니다. Claude Code에서 같은 에이전트로 스킬 유무를 비교했고, 실제 FastAPI + React 저장소를 포함한 39개 과제를 과제당 5회씩 돌렸습니다. Opus 5.5 기준입니다.

지표 Ponytail 5 스킬 없음 대비
코드 양 -53% 47~52%
시간 -41% 59~62%
비용 -26% 74~84%
토큰 -45% 55~57%
위험 로직 테스트 동반 98% 스킬 없을 때 68%

코드가 절반으로 줄었는데 품질은 올랐다는 게 이 프로젝트의 주장이며, 블라인드 비교에서 Ponytail 5의 답변이 스킬 없는 쪽(110 대 67)보다 선호됐다고 합니다. 보안 과제 6개(SQL 인젝션, 경로 탐색, 위조 토큰, 레이트 리밋, 깨진 CSV 행, 캐싱)는 30회 전부 통과했습니다. 측정 조건과 과제별 표는 저장소의 benchmarks/에 공개돼 있고, 이 수치는 프로젝트 자체 측정입니다.

어떤 작업에 맞나

이미 돌아가는 서비스의 작은 수정에 잘 맞습니다. 기존 코드가 충분하고, 요청이 명확하고, 검증 방법이 있는 작업이 그렇습니다. 반대로 새 시스템을 설계하거나 처음부터 구조를 잡는 작업에서는 최소 변경 원칙이 오히려 구조를 왜곡할 수 있습니다.

ultra 강도는 코드베이스가 개인적으로 잘못해 놨을 때 쓰라는 README의 표현처럼, 평소엔 full 기본값으로 시작하고 필요할 때 올리는 쪽이 자연스럽습니다.

한계와 주의

"필요 없다"는 판단은 사람마다 다릅니다. 스킬이 줄인 코드가 나중에 실제로 필요해지는 경우가 있습니다. 그래서 shortcut: 주석과 /ponytail-debt 장부가 있습니다. 리뷰에서 삭제 근거를 확인하는 절차가 필요합니다.

팀 규칙과도 부딪힐 수 있습니다. 저장소가 계층 분리를 강제한다면 최소 변경 원칙이 구조를 왜곡할 수 있으니, 스킬을 쓰더라도 저장소 규칙이 우선한다고 문서에 적어 두는 편이 안전합니다. 명령어는 스킬을 읽는 호스트에서만 동작하고, Cursor 같은 어댑터는 규칙 파일만 로드해 명령 없이 상시 규칙만 적용됩니다.

설치는 공식 경로(DietrichGebert/ponytail GitHub, npm의 @dietrichgebert/ponytail)만 쓰세요. README가 .exe나 .dll을 배포하는 복사본은 본인 것이 아니라고 못 박아 뒀습니다.

도입 전 체크리스트

확인할 것 4가지

✓ 규칙 우선순위 — 저장소 규칙이 스킬 판단보다 위인지 AGENTS.md에 명시

✓ 검증 — 줄어든 코드가 요구를 만족하는지 테스트로 확인

✓ 기록 — 삭제·축소 이유를 shortcut: 주석으로 남기고 /ponytail-debt로 추적

✓ 호스트 — 명령 지원 여부 확인(어댑터는 규칙만 로드될 수 있음)

정리

ponytail은 능력을 더하는 스킬이 아니라, 하지 않을 일을 정하는 스킬입니다. 코드 양이 문제라면 먼저 시험해 볼 만하고, "제일 게으른 시니어"의 판단 기준 — 이미 있는 것, 표준 라이브러리, 플랫폼 기능 — 은 스킬을 빼도 그대로 쓸 수 있는 원칙입니다.

오늘 해 볼 일은 하나입니다. 다음 작업에서 "이거 새로 만들어야 하나, 이미 있는 걸로 되나"를 먼저 물어보세요. 그 한 번의 질문이 ponytail의 전부입니다.
